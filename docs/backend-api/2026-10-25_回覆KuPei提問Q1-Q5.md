# 回覆 KuPei 提問 Q1–Q5（後端窗口）

日期：2026-10-25　收件：CoKu／KuPei
隨附（同一壓縮檔）：`KuPei-API.md`、`2026-10-23_KuPei前端串接規範.md`、`KuPei-前端部署指南-GitHub-Pages.md`、`openapi.json`、`starter/`。**Q3、Q5 的完整回覆在《串接規範》第 1、4 節，這裡是摘要。**

| # | 回覆 |
| --- | --- |
| **Q1** | GitHub Pages 上的網站就是 **KuPei 的正式前端入口**，由 KuPei 自行建置與部署（流程見《部署指南》）。沒有另一個「朋友的前端」——後端窗口只提供 API，不做前端。 |
| **Q2** | **維持權杖，不用 Cloudflare Access。** 原因：(1) Access 要掛在自有網域，目前服務在 `workers.dev`；(2) 前端在 `github.io`、API 在另一個網域，Access 的登入 cookie 跨站帶不過去，要改走 credentials 模式與重導流程，複雜度遠高於收益；(3) Access 的 service token 一樣是前端內嵌的祕密，沒有比較安全。現在有**兩把**權杖：唯讀權杖（進網頁，每 IP 每分鐘 30 次）與寫入權杖（CoKu 在 App 輸入、不進網頁，雲端文件用，每分鐘 60 次），都可隨時作廢。**作廢與重發流程**：KuPei 通知後端窗口 → 後端窗口作廢並重發（重新部署後舊權杖立即失效，約 5 分鐘）→ 新權杖以安全管道交付 → KuPei 更新 GitHub secret `VITE_KUPEI_TOKEN` 並重跑 workflow。若 KuPei 將來不想讓權杖出現在公開網頁，可改為**把前端掛回後端同源、走既有密碼登入**（無權杖、無 CORS），一句話即可切換，但前端就不在 GitHub Pages。 |
| **Q3** | **現行**：KuPei 交付批次檔 → 後端窗口以發布腳本驗證並產生 `manifest`＋`<run>/` → 部署 → 前端自動讀到。頻率＝KuPei 交付的頻率（目前預期每季一次）；收到後 1 個工作天內上線。**不能**由 KuPei 直接推送：批次是隨服務一起部署的靜態檔，沒有上傳端點。若日後頻率提高，可改為 KuPei 推到指定的私人 GitHub repo、由 Actions 自動發布，發布後再評估。**第一步請先交付 V3.0.29 的 UI 匯出樣本**（`summary`、`details`、`nodes`、`tr`、`vparams` 對應的來源檔各一份），後端窗口據此調整轉接；格式要求見《串接規範》第 4 節。 |
| **Q4** | 已隨本件一併提供（見上方隨附清單）。另有 2026-10-25 更新：批次檔請求帶 `?v=` 版本參數即可長期快取，`starter/kupei-client.ts` 已內建，細節在 `KuPei-API.md`「快取與載入」。 |
| **Q5** | 需求清單第 1～5 節已在《串接規範》第 1 節逐項回覆。**1-1、1-2 直接答**：後端窗口**不提供任何主機**，KuPei 的 FastAPI 與 SQLite 不部署在後端窗口這邊。但**寫入已由後端承接**（2026-10-25 上線）：自選同步、個股問題、新聞設定、報告排程設定全部走雲端文件 `/api/store`（整包 JSON＋版本鎖，跨裝置同步），前端照 `KuPei-API.md`「雲端文件」節串接即可，不需要登入系統。**仍不提供**：盤中 SSE 即時行情、報告的實際產生、估價與新聞的計算。這三項擇一：**(a)** 前端自理（即時行情直接接 FinMind；估價用批次的 `vparams` 在前端算）〔2026-10-27 更正：估價改由批次的可選檔 `valuation.json` 提供，前端只顯示、不計算；見《串接規範》§2〕；**(b)** KuPei 自己的主機（Tailscale）只跑 SSE 與報告產生這兩塊，前端同時連兩邊。由 CoKu 決定，後端窗口兩種都配合。 |
## 接下來請 KuPei 提供
1. GitHub Pages 來源 `https://<帳號>.github.io`（部署前）→ 後端窗口加白名單。
2. V3.0.29 的 UI 匯出樣本（Q3）。
3. Q5 的 SSE／報告產生選 (a) 或 (b)。
4. 寫入權杖交付對象（只給 CoKu 本人）與管道。
