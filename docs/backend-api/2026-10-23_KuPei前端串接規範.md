## 0. 一句話

後端只提供一個已上線的 API 服務（`https://kupei-dashboard.tmac19920626.workers.dev`）：評分批次與每日收盤行情**只讀**，使用者資料以**雲端文件**（`/api/store`，依帳號分開）整包存取。**前端只顯示、不計算**：排名、分數、Gate、估價都以後端給的為準。

## 1. 整體串接流程（從零到上線）

```
取得唯讀權杖 ──► 放 starter client ──► 讀 manifest ──► 讀批次檔（帶 ?v=）──► 讀行情
                                                                    │
部署 GitHub Pages ◄── 登記來源（CORS）◄── 雲端文件同步 ◄── 帳號登入／註冊 ◄┘
```

| 步驟 | 做什麼 | 規定 |
| --- | --- | --- |
| 1 權杖 | 後端窗口以安全管道給**唯讀權杖** | 只放 GitHub Actions secret `VITE_KUPEI_TOKEN`；本機放 `.env.local`（已在 `.gitignore`）。**不得**進原始碼、版控、issue、commit 訊息、AI 對話 |
| 2 客戶端 | 複製 `starter/kupei-client.ts`、`starter/kupei-types.ts` | **不得手改這兩個檔**。有 bug 或缺功能 → 回報後端，後端改 starter 後同步給你（見 §8）。轉成 UI 要的形狀請另寫一層（如 kupei-pages 的 `src/bridge.ts`） |
| 3 建立 client | `createKupeiClient({ baseUrl: VITE_KUPEI_BASE, token: VITE_KUPEI_TOKEN, onSessionChange })`，app 一啟動呼叫 `preload()` | 整個 app 只建一個 client |
| 4 manifest | `loadDataset()` 內部先讀 `/data/manifest.json` | manifest **每次都要重讀**（`no-cache`）；**不得**寫死批次編號 `run` |
| 5 批次檔 | `summary`、`tr`、`vparams`、`nodes`（必有）；`details/<代號>`（`loadDetail`）；`help`／`valuation`／`node_info`（可選，`loadHelp()` 等） | 網址帶 `?v=<manifest.hashes.對應鍵>`（details 用 `published_at`）。用 starter 就自動符合 |
| 6 行情 | `marketLatest()`、`marketHistory(codes)` | 只有每日收盤；**不得輪詢**（§2.5） |
| 7 帳號 | 登入／註冊畫面：`auth.config()` → `auth.register()`／`auth.login()`；`getSession()` 判斷狀態 | 評分與行情不需要登入；沒登入走本機模式，不報錯 |
| 8 雲端同步 | `store.get/put/update/remove` | 依 §3、§6 |
| 9 部署 | 照《KuPei-前端部署指南-GitHub-Pages.md》 | 正式來源必須先登記 CORS 白名單（目前已登記 `https://cobaltku.github.io`）；換網域要先通知 |
| 10 驗收 | 跑 §9 檢查清單 | 全部打勾才算上線 |

## 2. 接收資料的規定（後端 → 前端）

### 2.1 manifest 與快取
- 每次打開 app 都要重新驗證 `manifest.json`；它是「換批次」的唯一訊號。starter 會先用上次記住的批次畫面、背景核對，換了就呼叫 `onUpdate`——**必須**處理 `onUpdate`（重畫或提示「資料已更新」），否則使用者會停在舊批次。
- 批次資料夾發布後不變；同一個 `run` 的檔案靠 `?v=` 長期快取。**不得**自己拼不帶 `?v=` 的批次網址，也**不得**用 `published_at` 代替 `hashes` 當 summary／可選檔的版本。
- `manifest.hashes` 有四個固定鍵（`summary`、`vparams`、`tr`、`nodes`）＋可選鍵（`help`、`valuation`、`node_info`）。**沒有可選鍵＝檔案不存在，不得請求**（會 404）。不認得的新鍵忽略。
- `details/<代號>.json` 只有 `manifest.details` 列出的代號才有。

### 2.2 `summary.rows` 是固定順序的緊湊陣列
- 每列固定 **11 欄**、每個大項格固定 **8 欄**，順序見 `KuPei-API.md`「`summary.rows`」與附錄 A。一律經 `decodeRow()` 轉成具名欄位再用，**不得**在 UI 程式裡散寫 `row[4]` 這類索引。
- **不得假設 rows 會加欄。** 新的公司層級資料放 `summary` 頂層鍵（例如 `company_meta`），節點層級放 TreeNode 新鍵（例如 `goal`、`definition`、`peer_rank`）。這些都是**可能沒有**的：用之前檢查型別，缺了照常顯示。
- 回應欄位只增不減；前端必須容忍不認得的欄位與新的狀態字串（`ScoreStatus` 會新增）。

### 2.3 「有分數」與 null 的意義
| 值 | 意思 | 前端怎麼做 |
| --- | --- | --- |
| 大項格狀態是 `TRIAL_SCORE` 或 `POLICY_SCORE` **且**分數非 null | 有分數 | 只有這種才參與排序、底色（用 `hasScore()`） |
| 其他狀態（`UNAVAILABLE`、`NOT_APPLICABLE`、`OUT_OF_SCOPE_FINANCIAL`…或未知的新狀態） | 沒有分數 | 顯示狀態說明，排序放最後；**不得**當成 0 分 |
| 總名次 `null` | NR（不排名） | 排在最後，NR 之間依代號 |
| 行情 `收盤` 為 `null` | 當日無成交 | 顯示「—」，依價格排序放最後；**不得**拿前一日價格補 |
| 公司不在 `/api/market/latest.quotes` 裡 | 沒有行情（10 家已知找不到，見 `KuPei-API.md`） | 顯示「—」 |
| 排名母體 | `head.rank_population[大項索引]` | **不得**自己數母體 |

### 2.4 可選檔與「尚未提供」
- `help.json`、`valuation.json`、`node_info.json` 是批次的可選檔，內部形狀由批次交付方決定、後端不檢查。
- `loadHelp()`／`loadValuation()`／`loadNodeInfo()` 回 `null` → 該區塊顯示「尚未提供」或整塊不顯示。**不得**自行計算估價（`vparams.json` 只是參數說明表）、**不得**放假資料或空欄位、**不得**自己猜網址去抓。
- 內容形狀不認得時當成沒有（顯示「尚未提供」），不要讓畫面壞掉。

### 2.5 行情
- **只有每日收盤，不是即時。** 畫面要標「收盤價 M/D」之類的字樣，不得標成即時或延遲報價，也不得自己編時間（例如假設 13:30）。資料日期看 `latest.dates.L`（上市）／`dates.O`（上櫃）。
- 漲跌幅＝`漲跌價差 ÷ (收盤 − 漲跌價差)`（`quoteOf()` 已算）。
- `history`：一次 **1～30 個 4 碼代號**，重複的會去掉；**任何一個不合法就整個 400**（不會默默丟掉壞的）。用 `marketHistory()`，它會過濾、合併、分批、快取。
- **不得輪詢 `/api/*`。** 行情一天只更新幾次：`latest` 在 app 啟動、使用者手動「重新整理」、頁面從背景回到前景時各讀一次即可（starter 60 秒內共用同一份）。

### 2.6 前端不得重算
- 排名、分數、Gate、否決、財務複核、估價一律照後端給的顯示。前端只做**排序、篩選、搜尋、格式化**，規則照 `KuPei-API.md` 附錄 B（與本站畫面一致）：底色公式、前 10% 加粗、股價小數位、漲紅跌綠。

## 3. 送資料給後端的規定（前端 → 後端）

### 3.1 雲端文件 `/api/store/<key>`
| 項目 | 規定（數值以程式為準：`worker/store.ts`） |
| --- | --- |
| key 格式 | `^[a-z0-9][a-z0-9-]{0,39}$`（小寫英數與 `-`，1～40 字，開頭英數）；不合格 400 |
| 單份大小 | `data` 序列化後 ≤ **256 KB**；超過 413 `TOO_LARGE` |
| 請求本文 | 整個 PUT 本文（含 `baseVersion` 外殼）≤ **300 KB**；超過 413 `TOO_LARGE`（後端不讀完就拒絕） |
| 每個帳號額度 | 最多 **50 份**、所有文件合計 **2 MB**（UTF-8 位元組；覆寫以改完後的總量算，改小一定可以）。超過 403 `QUOTA_EXCEEDED`，`details` 是 `{ docs, bytes, maxDocs, maxBytes }`。**不得自動重試**，要提示使用者刪掉不用的資料 |
| 樂觀鎖 | PUT 本文 `{ baseVersion, data }`；`baseVersion` 必須等於雲端目前版本（第一次 0）。不符 409 `VERSION_CONFLICT`，`details` 是雲端最新整份文件 |
| 409 處理 | 用 `details` 的最新內容**合併**（能自動合併就合併，例如自選群組取聯集），或讓使用者選要哪一份；**不得**拿舊版本號硬覆蓋。`store.update(key, fn)` 會自動用最新內容重跑 `fn`（最多 3 次），`fn` 必須是純函式 |
| 刪除 | `DELETE /api/store/<key>?baseVersion=N`（N ≥ 1）：版本相符才刪；不符 409（附最新文件）、不存在 404（當成已刪除即可）。要清空請用 DELETE，**不要**寫 `data: null` 當刪除（那會留下一份 version > 0、內容 null 的文件，下次要用那個版本號寫） |
| 寫入頻率 | `/api/store*` 每個 IP 每分鐘 60 次。**必須**合併寫入（例如停手 1.5 秒後才送、一份資料一個 key 整包送），**不得**每次按鍵就 PUT |
| key 規劃 | 每種資料一個 key，整包存（例如 kupei-pages 現在用 `ui-watch`、`ui-news`、`ui-report`）。key 清單寫在前端文件裡，總數遠低於 50 |

### 3.2 帳號與密碼
- 帳號：3～32 字，只能用小寫英數與 `_` `.` `-`，開頭英數（伺服器先轉小寫再檢查）。前端送出前先 `trim()`＋轉小寫，並在畫面上說明規則。
- 密碼：8～128 字（以字元計，區分大小寫，前後空白也算，**不要** trim 密碼）。
- 邀請碼：打開註冊畫面時呼叫 `auth.config()`，`inviteRequired` 為 `true` 才顯示邀請碼欄位；若 config 失敗或後端回 403 `INVITE_REQUIRED`／`INVITE_INVALID`，也要把欄位顯示出來。
- 註冊、登入、改密碼、重設密碼合計每個 IP 每分鐘 10 次，登入與重設密碼另外每個帳號每分鐘 10 次：送出鈕要防連點，**不得**自動重送。

### 3.3 讀回來的資料一律當成不可信
雲端文件的內容任何持有該帳號登入權杖（或寫入權杖）的人都能改寫，後端**不檢查內容**。因此（2026-10-27 安全審查在 kupei-pages 找到並已修正的 XSS 就是這個來源）：
- 讀回 `store` 的資料（含合併進 `localStorage` 之後再讀的）**必須先驗證結構**：型別、長度、數量上限、代號格式（例如 kupei-pages `public/legacy/app.js` 的 `cleanW`／`cleanNS`／`cleanRS`），不合格的欄位丟掉、整份壞掉退回預設。
- 顯示到畫面一律跳脫（`textContent`，或 `innerHTML` 前用 `esc()`）；**不得**把使用者資料拼進 `href`、`style`、事件屬性或 `eval`。
- 批次檔的字串（公司名、`tr.json` 譯文、`help.json`）同樣跳脫後再顯示。

## 4. 錯誤處理

所有 JSON 錯誤都是 `{ "error": { "code", "message", "details?" } }`；starter 會丟 `KupeiError`（`status`、`code`、`details`、`retryAfter`）。前端依 `code` 決定行為，`message` 可以直接顯示給使用者看。

| 狀態／code | 前端行為 |
| --- | --- |
| 400 `BAD_REQUEST` | 前端送錯（格式、key、codes）。表單類顯示規則說明；其他是程式 bug，修程式，**不重試** |
| 401 `UNAUTHENTICATED`（登入權杖） | starter 已自動清掉 session 並呼叫 `onSessionChange(null)` → 畫面回到未登入、本機模式。**不得**用存起來的密碼自動重登（本來就不該存密碼） |
| 401 `UNAUTHENTICATED`（唯讀權杖） | 部署設定錯（secret 沒設或過期）→ 顯示「服務設定有誤，請聯絡維護者」，不要重試 |
| 401 `INVALID_CREDENTIALS` | 帳號或密碼不對（改密碼時＝目前密碼不對；重設密碼時＝帳號或重設碼不對、過期、已用過，一律提示「請向維護者重新索取重設碼」）。顯示錯誤，**不要登出** |
| 403 `FORBIDDEN` | 這個權杖不能用這個路徑（唯讀權杖打 `/api/store`、任何未文件化路徑）。**不得**重試或繞過 |
| 403 `QUOTA_EXCEEDED` | 顯示目前用量（`details`），請使用者刪資料；**不得**自動重試 |
| 403 `INVITE_REQUIRED`／`INVITE_INVALID` | 顯示邀請碼欄位／提示邀請碼不對 |
| 404 | `/data/*`：路徑錯或可選檔不存在（照 §2.1 本來就不該打）；store DELETE：當成已刪除 |
| 409 `VERSION_CONFLICT` | 照 §3.1 合併或讓使用者選 |
| 409 `USERNAME_TAKEN` | 請使用者換帳號名 |
| 413 `TOO_LARGE` | 提示資料太大（單份 256 KB）；**不重試**，要先縮小內容 |
| 429 `RATE_LIMITED` | 依 `Retry-After` 等待（預設 30 秒；跨來源時瀏覽器讀不到這個標頭，starter 會用 30 秒）。**只有 GET 自動重試一次**（starter 已做）；寫入交給使用者或下一次合併寫入 |
| 5xx、逾時（20 秒）、斷線 | 顯示「暫時無法連線」，保留本機資料；GET 可由使用者手動重試，或以遞增間隔（30 秒起、加倍、最多數次）重試；寫入保留 dirty 等下次 |
| 瀏覽器只顯示 CORS 錯誤（`TypeError`、沒有狀態碼） | 來源不在白名單、`/api/*` 請求沒帶 `Authorization`、或送了不允許的標頭（只允許 `Authorization`、`Content-Type`、`If-None-Match`）。**不得**改用 `no-cors` 硬解 |

**限流（以程式為準：`worker/index.ts`、`wrangler.jsonc`；每個 IP 計算，IPv6 以 /64 為一組，同一台電腦的所有分頁共用）：**
| 範圍 | 每分鐘上限 |
| --- | --- |
| `/api/market/*`、`/api/auth/logout`、`/api/auth/me`、`/api/auth/config`、其他帶權杖的 `/api/*` | 30 |
| `/api/store`、`/api/store/<key>` | 60 |
| `/api/auth/register`＋`login`＋`password` 合計 | 10（`login` 另外每個帳號 10） |
| `/data/*` | 唯讀權杖不限；用登入權杖時偶爾會計入上面的 30 次（後端查一次登入狀態），所以建議 `/data/*` 一律交給 starter，不要自己大量平行抓 details |

Cloudflare 的限流是各節點的近似計數，實際門檻不保證剛好是這些數字；前端不要設計成「剛好卡在上限」。

## 5. 帳號與同步

### 5.1 權杖的存放與清除
| 權杖 | 存在哪 | 誰能放 | 清除 |
| --- | --- | --- | --- |
| 唯讀 | 建置產物（來自 GitHub secret） | 部署流程 | 後端作廢重發 → 更新 secret 重新建置 |
| 登入（`kps_…`，30 天，不自動續期） | `localStorage` 的 `kupei:session`（starter 管理） | 只能經 `auth.login()`／`register()`／`changePassword()` | `auth.logout()`；過期或 401 時 starter 自動清 |
| 寫入（舊做法，相容保留） | `localStorage` 的 `kupei:write-token` | 只能由使用者在設定畫面貼上 → `setWriteToken()` | `setWriteToken(null)` |

- 權杖優先順序：登入 ＞ 寫入 ＞ 唯讀（starter 自動選）。
- 前端**不得**自己另存權杖或密碼、不做「記住密碼」；改密碼成功後清空畫面上的密碼欄位。
- App 啟動時建議呼叫一次 `auth.me()` 確認登入仍有效（失效會自動清 session）。

### 5.2 換帳號不得把前一個帳號的資料上傳
同一台瀏覽器可能先後登入不同帳號，`localStorage` 裡的資料不屬於「現在登入的人」。**必須**記錄本機資料屬於誰，換人時不得上傳。kupei-pages 目前的做法（`src/bridge.ts`）可作為範例：

1. 本機資料 key（`kupei3_watch` 等）對應雲端 key（`ui-watch` 等），雲端內容是 `{ savedAt, value }`。
2. 另存一份 meta（`kupei3_sync`）：`owner`（最後同步的帳號；寫入權杖算一個 owner）、各文件已同步的 `versions`、還沒推上去的 `dirty`。**登出時不清 owner。**
3. 登入（或啟動時已登入）先 `pullAll()`：若 `owner` 不是現在的帳號 → 本機資料備份到 `*_prev`、清空、版本歸零、先寫回 meta，之後**只載入雲端、不上傳**。
4. 同一個帳號：雲端版本比上次新 → 以雲端為準，本機未推的那份留在 `*_conflict` 供救回；雲端沒有、本機有 → 才把本機上傳（第一次同步）。
5. 平常寫入：攔 `localStorage.setItem` 標 dirty，停手 1.5 秒後 `pushDirty()`；推之前再確認 owner 沒變；pull／push 用佇列串行，不並行。
6. 改寫本機後畫面要重新載入，期間（`frozen`）丟掉畫面送來的舊寫入。

自己重寫同步時，第 3 點（換人不上傳）與第 4 點（衝突保留本機副本）是硬規則，其餘可依框架調整。

### 5.3 改密碼、停用、寫入權杖
- 改密碼成功後**這個帳號所有裝置的登入權杖都失效**；這台由 starter 自動換成新權杖（`onSessionChange` 會收到同帳號、新 `expiresAt`），別台下一個請求收到 401 → 回到未登入。畫面上要先告訴使用者這件事。
- 帳號可能被維護者停用（所有裝置登出、之後登入一律 401 `INVALID_CREDENTIALS`）。忘記密碼（2026-10-27）：使用者向維護者拿一次性重設碼（24 小時、只能用一次），在登入畫面的「忘記密碼」輸入帳號、重設碼、新密碼，呼叫 `kupei.auth.resetPassword()`；成功後所有裝置登出、這台直接是登入狀態，畫面上的密碼與重設碼欄位要清空。沒有刪除帳號、Email 驗證。
- 寫入權杖是帳號功能之前的相容做法：所有持有者共用一份文件（owner `kupei`），與任何帳號的文件**互相看不到**。新功能一律以帳號為主；要把寫入權杖那份搬到帳號，必須由使用者明確操作（讀出 → 寫進帳號），不得自動搬。

## 6. 安全

- **唯讀權杖會公開在網頁裡**，任何打開網頁的人都拿得到；它只能讀評分與行情，所以可以接受。網址不要到處散布。
- **登入權杖與寫入權杖只存在使用者自己的裝置。** 不得放進建置、環境變數、repo secret、原始碼、URL（含 query 與 hash）、`console.log`、錯誤回報、分析工具或任何第三方服務。錯誤訊息裡也不要帶 `Authorization` 標頭。
- `innerHTML` 一律跳脫（§3.3）。不要載入不信任的第三方 script：同一個頁面的任何 script 都讀得到 `localStorage` 裡的權杖。
- **`cobaltku.github.io` 同來源共用的風險**：GitHub Pages 同一個帳號底下的所有 repo 都是同一個來源 `https://cobaltku.github.io`，共用同一份 `localStorage`，也都在 CORS 白名單內。該帳號底下任何其他 repo（包括之後新開的、或被放了不信任程式的）都讀得到 `kupei:session` 與 `kupei:write-token`。因此：
  - 這個帳號底下**不要**放不信任或來路不明的頁面；
  - 長期建議改用專用網域（或獨立的 GitHub 帳號／組織）放 KuPei，換網址前先通知後端窗口登記新來源。
- 疑似權杖外流：立刻通知後端窗口作廢重發；登入權杖外流時請使用者改密碼（所有裝置登出）。

## 7. 不在範圍內（後端不提供）

- 盤中即時行情、SSE 推送（只有每日收盤）。
- 估價、新聞、個股報告的**計算與產生**；報告排程的**執行**（設定可以存在 `/api/store`，後端不會跑）。
- 檔案上傳（例如報告附件）。
- 主機、SSH、Tailscale；KuPei 自己 FastAPI 的端點（`/api/v1/*`、`/quotes/stream`、`/reports/*`）**不是**本服務的一部分。
- 站長的內部端點（`/api/watchlist`、`/api/me`、`/api/market/sync`、`/api/admin/*`）：任何權杖都是 403。

需要以上功能只有兩種做法：(a) 前端自理、不經後端（例如即時行情自己接 FinMind，條款與額度自行確認）；(b) 以書面提出需求（§8），後端回覆前視為不提供。

## 8. 變更與溝通

- **後端變更怎麼通知**：契約（`KuPei-API.md`、`openapi.json`、本文件、`starter/`）的正本在後端 repo；有變更時，後端會對 kupei-pages 開 PR，更新 `docs/backend-api/` 與 `src/kupei-client.ts`、`src/kupei-types.ts`，PR 說明寫明日期與影響。前端合併後依 PR 調整。
- **只能使用 `KuPei-API.md` 列出的端點**。未列出的路徑一律視為不存在：不得探測、不得依賴、不得從錯誤訊息或回應猜功能。
- **前端有新資料需求**（新欄位、新端點、改上限）：寫進 kupei-pages 的 `docs/後端建議.md`（寫清楚：要什麼、畫面怎麼用、急不急），通知後端窗口。後端回覆可否與時程前，**視為不提供**，前端不得先做假資料或預留假端點。
- **starter 有問題**：在 `docs/後端建議.md` 記錄現象與重現方式，不要在前端 repo 直接改 `src/kupei-client.ts`／`src/kupei-types.ts`（下次同步會被蓋掉）。急用可以在自己的橋接層繞過，但要註明並回報。
- **評分批次更新**：KuPei 交付批次檔 → 後端窗口發布 → `manifest.run` 改變，前端不需改程式（§2.1 的 `onUpdate`）。格式不同時先交付樣本。
- 回應欄位只增不減；要移除或改變既有欄位，後端會事先書面預告並以新版本路徑提供。
